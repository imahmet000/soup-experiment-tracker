# Приём метрик — формат и поведение

## Путь события

Программа отправляет пакет в `POST /api/runs/{run_id}/metrics` с API-ключом проекта. Пакет содержит стабильный `batch_id` и один или несколько событий. Каждое событие содержит стабильный `event_id`, `metric_name`, числовое `value` и необязательный `client_time` с часовым поясом.

```json
{
  "batch_id": "uuid пакета",
  "events": [
    {
      "event_id": "uuid события",
      "metric_name": "accuracy",
      "value": 0.91,
      "client_time": "2026-11-10T10:00:00Z"
    }
  ]
}
```

`server_seq` назначается сервером отдельно для каждого запуска в момент приёма, внутри транзакции с блокировкой строки запуска. Это порядок журнала и SSE-потока. Клиентское время сохраняется как метаданные: позднее событие не переставляет уже выданные номера.

## Повторная отправка

Хэш канонического содержимого пакета сохраняется вместе с квитанцией `(run_id, batch_id)` в той же транзакции, что и метрики.

- Новый `batch_id`: вставить новые события, назначить последовательности и сохранить квитанцию.
- Уже принятый `batch_id` с тем же содержимым: вернуть сохранённое подтверждение без повторной записи.
- Уже принятый `batch_id` с другим содержимым: `409 Conflict`.
- Уже встречавшийся `event_id` с теми же данными в другом пакете: вернуть его прежний `server_seq`, не применять второй раз.
- Уже встречавшийся `event_id` с другими данными: `409 Conflict`.

Если любой шаг записи завершается ошибкой, PostgreSQL откатывает всю транзакцию. Частично сохранённой пачки не остаётся.

## Снимок и восстановление SSE

Страница одним запросом получает снимок запуска и курсор `C = next_seq` из согласованного снимка базы. После этого она подключается к `/api/runs/{id}/events?after=C` и получает только события с `server_seq > C`. Каждое SSE-сообщение имеет `id`, равный `server_seq`.

При разрыве браузер хранит последний применённый `server_seq` и при переподключении снова запрашивает события после него. Сервер проверяет журнал PostgreSQL каждые 0,5 секунды. События, появившиеся во время отключения, остаются доступными в базе; отдельной очереди в памяти нет.

## Граница проекта

API-ключ однозначно определяет проект. Каждый запрос чтения, записи и подписки проверяет, что `run.project_id` равен проекту ключа. ID запуска не даёт прав. Отсутствующий и чужой запуск дают одинаковый `404`. Общего кэша нет.

Создание проекта открыто для локальной демонстрации: оно выдаёт новый проект и ключ, но не открывает доступ к существующим проектам. Для публичного сервиса перед этим нужен вход владельца и защита от массового создания проектов.

## Что тесты не доказывают

Интеграционные тесты проверяют бизнес-правила и серверный поток. Они не доказывают отсутствие временных каналов утечки, поведение браузера на всех движках или целевую производительность. Для заключения о 50 запусках × 10 событий/с требуется отдельный нагрузочный прогон с сохранённым сырым выводом и сверкой результата с базой.

Нагрузочный прогон на 10 секунд создал 50 запусков и 50 одновременных SSE-подключений, отправляя по 10 событий в секунду в каждый запуск. Все 5 000 событий приняты; каждый SSE-поток получил номера 1–100 по порядку, а снимок каждого запуска совпал с ожидаемым числом событий. Ошибок и расхождений нет; p95 HTTP-запроса — 57,9 мс, максимум — 84,4 мс. Сырой вывод сохранён в `outputs/load-results.txt`.

Вердикт: **ВЫПУСКАТЬ** для этой нагрузки по результату данного прогона. Перед увеличением нагрузки сначала провести более длительный прогон и добавить наблюдение за задержкой, отставанием SSE и ожиданием соединений с базой. Тестовый набор по-прежнему не доказывает отсутствие тайминговых утечек или устойчивость при длительной деградации сети.
